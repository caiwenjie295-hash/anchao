## 1. 先看结论

当前项目能通过主要自动门禁，但离线交付物采用“把应用、样式和图片全部写进一个 HTML”的方式，已经形成明显的内存和构建结构风险。

最直接的事实是：

- 根目录 `暗潮.html` 当前为 **76,455,416 bytes / 72.91 MiB**。
- 该 HTML 内含 **35 个 `data:image/...;base64,...` 图片数据**；仅 Base64 字符就约 **54.19 MiB**，还没有算 HTML、JavaScript、CSS、解析中间对象和解码后的位图。
- 当前 `npm run test:offline` 必须把这个大 HTML 整体读入 jsdom，并执行两轮连续流程；本次通过，但执行过程超过 1 分钟，且每个测试文件都创建独立 jsdom 环境。
- 正常 Vite 构建已经会把图片放进 `dist/assets/`，但离线构建脚本另走 `lib + IIFE + writeFile` 路径，将所有内容重新拼回单文件，造成两套构建语义不一致。
- `npm run build` 当前还提示 JavaScript 主 chunk 超过 500 kB；没有硬性的包体积、首屏加载或峰值内存预算。

因此，优先级最高的工作是：保留 React/数据驱动架构，把离线交付改为“相对路径入口 + 外置脚本/样式/图片资源”，并给构建和离线测试增加资源清单、体积预算和 `file://` 兼容检查。

## 3. 当前命令入口

`package.json` 当前脚本如下：

| 命令 | 实际行为 | 当前问题/边界 |
| --- | --- | --- |
| `npm run dev` | 启动 Vite 开发服务器 | 只验证服务模式，不验证双击 `file://` 入口 |
| `npm test` | `vitest run`，扫描 `src` 下的 `*.test.*` | 所有测试默认使用 jsdom；没有 unit / acceptance / browser 分组和覆盖率门禁 |
| `npm run build` | `tsc -b && vite build`，生成 `dist/` | 正常构建是资源拆分的，但只有一个约 596 kB 的 JS 主 chunk，并且只给出 warning |
| `npm run build:offline` | `tsc -b && node scripts/build-offline.mjs` | 使用 Vite library IIFE，把 CSS、JavaScript、图片数据再次拼成根目录单 HTML |
| `npm run test:offline` | `node scripts/verify-offline.mjs` | 读取已生成的 `暗潮.html`，在 jsdom 中执行 A–K、存档/重载、清零和 T01–T06 流程；不是独立的浏览器 `file://` 测试 |
| `npm run quality:gate` | `bash scripts/quality-gate.sh` | 依赖 Bash；脚本只检查 Git diff 禁止路径和现有四项命令，没有体积/内存预算 |

### 3.1 现有离线构建流程

当前 `scripts/build-offline.mjs` 的核心逻辑是：

1. 调用 Vite 的 `build()`，使用 `lib: { entry: 'src/main.tsx', formats: ['iife'] }`。
2. `write: false`，把构建返回的 chunk 和 CSS asset 读到 Node 内存。
3. 把 CSS 放进 `<style>`，把 JavaScript 放进 `<script>`。
4. 把所有被打包的图片资源作为 Base64 数据放入 JavaScript/HTML。
5. 写出根目录 `暗潮.html`。

这条链路为了实现“单文件双击运行”很直接，但它同时会在构建阶段和运行阶段制造多个大对象：原始资源、编码字符串、拼接后的 HTML 字符串、浏览器解析后的 DOM 字符串和解码后的图像对象。

### 3.2 现有离线验证流程

`scripts/verify-offline.mjs`：

- 直接 `readFile('暗潮.html', 'utf8')`，把整个离线文件加载到 Node 字符串。
- 创建 `JSDOM`，使用 `runScripts: 'dangerously'` 执行内嵌应用。
- 通过 `requestInterceptor` 拦截请求，把非 `data:` 请求记录并拒绝。
- 默认执行两轮：第一轮覆盖第一幕 A–K、照片编辑、保存/重载、结局、清零和第二幕 T01–T06；第二轮回归第一幕和清零。
- 直接断言图片是 `data:image/...;base64,...`，这使测试与“所有图片内嵌”的实现强绑定。
- 测试使用合成 origin `https://anchao-offline.test`，并非真实浏览器双击 `file://`。

## 5. 内存溢出问题的证据链

### 5.1 已确认的体积来源

- `src/` 当前共有 47 个静态 PNG/JPG 文件，合计约 **80.16 MiB**。
- `data/images.json` 和 `import.meta.glob(..., { eager: true, query: '?url' })` 会让被登记的资源在构建时全部进入依赖图。
- 离线构建把 35 个图像 URL/内容变成 Base64 后塞进一个 JavaScript/HTML 字符串。
- Base64 本身约比二进制大三分之一；随后浏览器还要把字符串重新解析并解码为图像。

### 5.2 可能的峰值放大点

下面是根据构建链路可以确认的对象复制路径；它们解释了为什么“磁盘只有 73 MiB”仍可能触发数百 MiB 甚至更高的峰值：

```text
原始 PNG/JPG
  -> Vite/Node 读取的 Buffer
  -> Base64 字符串
  -> 拼接中的 JavaScript 字符串
  -> 76 MiB HTML 字符串
  -> 浏览器/jsdom HTML 解析树
  -> data URL 字符串
  -> 解码后的图片位图
```

当前没有可靠的浏览器峰值 RSS/JS heap 采样，也没有 CI 内存预算，所以不能把上述放大路径写成一个精确的“溢出阈值”。可以确定的是，当前实现把所有图片放在首次解析路径上，峰值随资源总量线性增长，且测试会重复建立解析环境。

### 5.3 当前实现的实际表现

- `npm run build:offline` 能通过，但它只代表 Node 构建阶段没有失败，不代表低内存机器能顺利双击打开。
- `npm run test:offline` 能通过，但它是 jsdom 合成 origin，不覆盖真实 Chrome/Edge 对 `file://`、图片解码和渲染进程内存的行为。
- 生成的 `暗潮.html` 没有进入 Git，由脚本随时重建；因此仓库中没有一个可直接 diff 的离线产物，也没有自动记录入口大小变化。

## 6. 构建、文件结构和测试结构中的主要不规范点

### 6.1 构建目标有两套语义

正常 `npm run build` 使用 Vite 应用构建，得到 `dist/index.html + dist/assets/*`；离线 `npm run build:offline` 改用 Vite library IIFE，再手工拼 HTML。两条路径不是同一个产物的不同包装，而是两套不同的打包模型，容易出现：

- 在线能加载、离线不能加载；
- 相对路径、`file://` 路径和资源查询方式不一致；
- 一个路径能做 chunk splitting，另一个路径重新合成单大文件；
- 测试只盯着生成的单文件，无法验证正常构建的实际资源清单。

### 6.2 资源加载是 eager 全量依赖

`src/core/assetLoader.ts` 使用 eager glob 扫描图片。它适合保证资源 ID 稳定和离线可用，但没有按场景、应用或页面延迟加载的层级。离线拆包时应保留“资源 ID → 相对 URL”的契约，把二进制文件从应用入口和主脚本中移出。

### 6.3 测试分层不够清晰

当前 35 个测试文件按 `data / story / scenes / modules / core / components` 分布，但只有一个 `npm test` 入口：

- 数据单元测试、StateManager/SaveManager 测试、React 组件测试、跨阶段验收测试混在同一 Vitest 运行中；
- 所有测试默认 jsdom，组件和状态测试的环境初始化成本重复；
- 没有单独的 browser smoke/e2e 命令；真实浏览器检查主要依赖人工走查；
- 没有覆盖率阈值、包体积阈值或内存回归阈值；
- 离线脚本是另一套 Node/jsdom 测试，不共享明确的 fixture、阶段驱动器或报告格式。

### 6.4 离线测试绑定旧实现细节

`verify-offline.mjs` 直接断言 `data:image/...;base64`，导致测试验证的是“图片必须内嵌”，而不是“图片可以从本地相对路径加载且不联网”。这会阻碍合理拆包，也使测试无法表达新的离线契约。

### 6.5 质量门禁没有资源和内存检查

`quality:gate` 当前主要检查 Git diff、禁止生成物提交，并执行四个命令。它没有：

- 入口 HTML 最大字节数；
- JS/CSS 最大 chunk；
- 总资源大小和单张图片大小；
- 外部 URL / CDN 依赖检查；
- `file://` 启动 smoke；
- 构建进程或真实浏览器的峰值内存记录。

### 6.6 工作区状态影响结论

当前 `main` 有大量未提交和未跟踪内容，且多个 worktree 并行存在。若不先固定提交 SHA 和干净工作区，测试通过不能准确回答“哪个版本通过”。

## 7. 建议的低风险改造方向

建议按下面顺序拆分，先解决离线内存问题，再逐步优化测试结构：

### 阶段 A：离线包改成目录交付

默认输出：

```text
暗潮离线/
  index.html
  manifest.json
  assets/
    app.js
    style.css
    *.png
    *.jpg
```

要求：

1. 构建使用相对路径 `./assets/...`，明确设置 Vite `base: './'`；不能使用 `/assets/...` 这种站点根路径。
2. 入口只放很小的 HTML，不内嵌全部图片。
3. 允许保留一个 IIFE `app.js` 以兼容双击 `file://`，但图片、字体和大型资源必须外置。
4. 不依赖软链接、不依赖本地服务器、不引入 CDN 或网络请求。
5. `manifest.json` 记录入口、资源清单、字节数和构建版本。
6. `暗潮.html` 若要保留，只作为显式兼容回退，不再作为默认交付物。

### 阶段 B：把离线验证改成资源契约测试

`test:offline` 应验证：

- `index.html` 存在且小于预算；
- 所有脚本、样式、图片引用都是相对路径；
- 不存在 `http://`、`https://`、CDN 或未登记资源；
- manifest 中列出的每个文件都存在，大小与报告一致；
- 入口可以在真实浏览器以 `file://` 打开；
- 网络拦截时仍能完成核心流程；
- 缺图时显示本地回退而不是破图。

不要再把 `data:` 图片作为必须条件。测试应断言资源可达和行为正确。

### 阶段 C：测试分层

建议新增明确入口：

```text
npm run test:unit        # data/core 纯逻辑
npm run test:component   # React + jsdom
npm run test:acceptance  # 第一幕/第二幕连续流程
npm run test:offline     # 目录离线包 + file:///网络拦截
npm run test:browser     # 宽屏真实浏览器 smoke
```

先保持现有 `npm test` 作为全量兼容入口，待分层稳定后再调整默认门禁。共享的流程 fixture 和保存数据应集中管理，避免每个大验收文件重复手写整段点击序列。

### 阶段 D：建立预算和观测

建议在构建结束生成机器可读报告并设初始预算：

- `index.html`：例如不超过 64 KiB；
- `app.js`：例如不超过 1 MiB，超过则要求拆 chunk；
- 单张图片：例如不超过 4 MiB；
- 总资源：单独记录，不把它误当成入口内存；
- 真实浏览器首次打开：记录打开耗时、控制台错误和渲染进程峰值内存；
- CI/本机 Node 构建：记录 RSS、heapUsed、external memory 和构建耗时。

预算数值应基于一次干净基线测量后确定，不能直接套用示例数字。

## 10. 当前结论

当前代码的剧情、状态和界面自动测试覆盖已经形成一定基础，`main` 工作区本次四项基本命令均能完成；但离线包把所有资源塞入单个 HTML，导致入口体积、解析内存、测试等待时间和构建路径耦合在一起。下一步应先建立干净基线，再把离线交付改成目录包，并同步重写离线资源契约测试；不要在未测量真实 `file://` 行为和内存峰值前直接把“单文件通过”当成低内存兼容。
