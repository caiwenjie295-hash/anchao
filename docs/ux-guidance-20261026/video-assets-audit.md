## 复现与审计结论

1. 在受访视频播放器从 0ms 依次定位 `4000`、`6500`、`6800`、`8601`、`9000`，逐次核对屏幕 `data-asset-id` 与实际显示图。6500ms 仍显示行走图，6800ms 才显示 005，8601ms 显示 008，9000ms 切回 003。
2. 在 6800–8600ms 截图可得到 `FRAME_A2_T07_001`，图片与时刻均来自当时实际显示的 005；在树林关键帧截图得到 `FRAME_A2_T07_002`，只对应树林观察。截图数据保存 frame ID 与实际时刻，不生成另一张图片。
3. 在对照页逐一选择树林截图、破庙截图并打开对应旧照片；树林参照保持“环境相似，不足以确认”，破庙截图才进入建筑对照。两侧对照图和 caption 随所选 frame 更新。
4. `IMG_A2_T07_004` 有一项可核对的元数据差异：山路 segment 的 `imageId` 指向 004，但实际显示时间由 `visualFrames` 指定为 4000–6800ms 的 `IMG_A2_T07_TRAIL_WALK_001`、6800–8601ms 的 005；004 当前不是可见播放器帧。已看过 004 原图，未发现可据此证明当前显示为错图的证据，因此不改冻结时间窗或素材映射。若产品意图要求 6500ms 立即出现石砌结构，需由父基于剧情/时间合同决定是否补充修改授权。
5. 对项目文件列表查找 `.mp4`、`.mov`、`.webm`、`.m4v` 未发现 T07 原始视频；当前实现使用静态帧。故无法做原始影片逐帧比对，也没有将未复现的猜测写成已修复错误映射。
6. 慢载浏览器验收曾在从 6500ms 播放跨段、随后回到已载入过的 003 时复现“图片已 complete 但仍 loading”。修复提交 `3096b46d6d009e9dad9984e50a7680160f8ffe60` 同步检查缓存图尺寸且不再被 passive effect 覆盖；父已在真实浏览器确认可连续播放到 16000ms、完成 2/2 段覆盖，没有再次卡住。父最终复验端点显示“播放结束/重新播放”，按钮及播放器焦点空格键都从 16000ms 手动回到 0ms；HTTP 慢载 6 秒期间暂停后，图片就绪仍停留在 6900ms。对照外景 HTTP 503 时，观察/特征/提交均 disabled，真实重试恢复后仍保留 6900ms 截图。`654d2b0ec7851a8834f7d46f5a76155bd7f2fc40` 与 `0eacd7165f1e8faaee16f46dbd966a2cc0f4d30b` 有组件回归和父的真实浏览器复验。
